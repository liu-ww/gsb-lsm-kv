# lsmkv 磁盘格式说明（字节级）

本文档描述 lsmkv 的三类持久化结构：**WAL 记录**、**SSTable 段文件**、**稀疏索引**
（稀疏索引内嵌在 SSTable 中，但单独成节说明），以及段清单 **MANIFEST**。

约定：

- 所有整数均为**小端序（little-endian）**。
- `u8` = 1 字节，`u32` = 4 字节无符号，`u64` = 8 字节无符号。
- 偏移量均相对于文件起始，按字节计。
- 校验和统一使用标准库 `zlib.crc32`（IEEE CRC-32），覆盖范围逐节注明。
- key/value 均为原始 `bytes`，长度前缀，完全二进制安全（可含 `\x00`）。

---

## 1. WAL 记录（`wal-NNNNNNNN.log`）

WAL 是一个**只追加**的帧序列，没有文件头。每条提交的写入（`put` 或 tombstone
`delete`）对应一条定长 25 字节头 + 变长 key/value 的记录。写入后立即
`flush + fsync`，fsync 返回成功才算提交。

### 1.1 单条记录布局

```
偏移      长度   类型   字段          含义
─────────────────────────────────────────────────────────────────
0         4      u32    magic         固定 0x57414C31，ASCII "WAL1"
4         4      u32    crc32         本记录 body（偏移 8 起到记录末尾）的 CRC-32
8         8      u64    sequence      全局单调递增版本号（同 key 越大越新）
16        4      u32    key_len       key 字节数 K
20        4      u32    value_len     value 字节数 V（tombstone 时为 0）
24        1      u8     flags         位域：bit0 = 1 表示 tombstone（删除）
25        K      bytes  key           原始 key 字节
25+K      V      bytes  value         原始 value 字节；tombstone 时该字段为空
─────────────────────────────────────────────────────────────────
记录总长 = 25 + K + V
```

> 头部结构等价于 `struct.Struct("<IIQIIB")`，`size == 25`（无填充）。

### 1.2 CRC 覆盖范围

CRC 从 **偏移 8**（`sequence` 字段）开始，覆盖到记录最后一个 value 字节，即
不含前 8 字节的 `magic` 和 `crc32` 本身：

```
crc32( data[8 : 25+K+V] )
```

### 1.3 崩溃 / 撕裂（torn write）恢复规则

重放时从偏移 0 逐条帧顺序解析：

1. 剩余字节 `< 25`（头都不完整）→ 判定为尾部撕裂，**停止**，只丢这一截。
2. `magic` 不匹配 → 该帧未完整落盘，判定为尾部撕裂并停止。
3. `25 + key_len + value_len` 超出文件实际剩余长度 → 帧体被截断，停止。
4. 帧完整但 CRC 不匹配：
   - 若该帧恰好位于文件末尾 → 视为撕裂尾部，丢弃；
   - 否则属于**已提交数据损坏**，抛出 `WalCorruptError`，绝不舍弃已确认的写入。

重放同时返回有效前缀长度，DB 打开时会把撕裂尾部**物理截断**，保证后续状态干净。

### 1.4 WAL 代际与截断

- 文件名 `wal-00000001.log` 起，代际号 8 位十进制补零。
- memtable 冻结（约 4MB）时新建下一代 WAL；老 memtable 刷成 SSTable 并在
  MANIFEST 原子发布（且 fsync）之后，对应旧 WAL 文件才被删除（等价于"截断整代"）。
- 崩溃若发生在旋转窗口，恢复时按代际号顺序重放所有存活 WAL，新版本号覆盖旧值。

## 2. SSTable 段文件（`seg-NNNNNNNN.sst`）

SSTable 由一次 memtable 刷盘或一次压实产生。条目严格按 **key 升序**存储，
value 连同 tombstone 标记一起持久化。文件三部分顺序排列：

```
偏移 0 ┌──────────────────────┐
       │  data blocks（数据块）│  每块最多 64 个条目，每块独立 CRC-32
       ├──────────────────────┤
       │  index region（索引区）│  稀疏索引条目 + 索引区 CRC
       ├──────────────────────┤
       │  footer（页脚）        │  定长前缀 + 变长 min/max key + CRC + 长度
 文件末 └──────────────────────┘
```

段文件先写 `seg-*.tmp` 并 fsync，再用 `os.replace` 原子改名为正式文件，随后
fsync 目录，保证崩溃时目录项一致。

### 2.1 条目编码（数据块内）

每个 key-value（含 tombstone）编码为 17 字节定长头 + 变长载荷：

```
偏移   长度  类型  字段         含义
─────────────────────────────────────────────────────────────
0      8     u64   sequence     版本号
8      4     u32   key_len      K
12     4     u32   value_len    V（tombstone 时为 0）
16     1     u8    flags        bit0 = 1 表示 tombstone
17     K     bytes key
17+K   V     bytes value        tombstone 时为空
─────────────────────────────────────────────────────────────
条目长 = 17 + K + V
```

结构等价于 `struct.Struct("<QIIB")`。

### 2.2 数据块布局与块级校验

一个数据块 = 最多 **64** 个连续的已编码条目，其后紧跟 4 字节块 CRC：

```
块内偏移   长度        字段
────────────────────────────────────────────────────────
0          B           block body：64 个（或末块不足 64 个）条目拼接
B          4  u32      crc32(block body)   ← 仅校验块体，不含自身
────────────────────────────────────────────────
块总长度（磁盘） = B + 4
```

读取时对块体重算 CRC-32，与尾部 4 字节不符即抛 `SSTCorruptError`。
点查只读取稀疏索引定位到的**一个**块。

### 2.3 稀疏索引区（index region）

索引区紧跟所有数据块。每**一个数据块**对应一条稀疏索引项，因此密度为
**每 64 个 key 一个索引点**。所有索引项拼接为索引体，末尾追加 4 字节 CRC：

单条索引项：

```
偏移   长度  类型  字段             含义
──────────────────────────────────────────────────────────────
0      8     u64   block_offset     该块在文件中的起始字节偏移
8      4     u32   block_len        块**体**长度 B（不含 4 字节 CRC）
12     4     u32   first_key_len    该块第一个 key 的长度 FK
16     FK    bytes first_key         该块首条条目的 key（索引锚点）
──────────────────────────────────────────────────────────────
索引项长 = 16 + FK
```

索引区整体：

```
偏移(相对索引区)  长度              字段
────────────────────────────────────────────────────────
0                 I                 index body：各索引项顺序拼接
I                 4      u32        crc32(index body)
────────────────────────────────────────────────────────
索引区磁盘长 = I + 4
```

点查定位算法：对索引项的 `first_key` 做二分，取最后一个
`first_key <= 目标 key` 的块；读出该块后在块内对有序条目再做一次二分。

### 2.4 Footer（页脚）

Footer 位于文件末尾，含一个 44 字节定长前缀和变长 min/max key：

```
偏移(相对 footer) 长度  类型  字段                含义
────────────────────────────────────────────────────────────────────
0                 4  u32   magic                0x53535431，ASCII "SST1"
4                 4  u32   version              当前为 1
8                 8  u64   index_end            索引区结束偏移（= footer 起始偏移）
16                8  u64   index_len            索引区磁盘长度（含 4 字节 CRC）
24                8  u64   index_region_start   索引区起始偏移
32                4  u32   entry_count          段内条目总数
36                4  u32   min_key_len          最小 key 长度 MN
40                4  u32   max_key_len          最大 key 长度 MX
44                MN bytes     min_key          段内最小 key
44+MN             MX bytes     max_key          段内最大 key
44+MN+MX          4  u32   footer_crc           对其之前所有 footer 字节的 CRC-32
48+MN+MX          4  u32   footer_len           footer 总长度（含本字段）
────────────────────────────────────────────────────────────────────
footer_len = 44 + MN + MX + 4(crc) + 4(len) = 52 + MN + MX
```

打开段文件时先读末尾 4 字节得到 `footer_len`，再整体读取 footer，校验 magic、
version 与 footer CRC，然后定位并校验稀疏索引。

### 2.5 一个 200-key 段的示意

```
[ block0: key 000..063 ][crc] [ block1: 064..127 ][crc]
[ block2: 128..191 ][crc]   [ block3: 192..199 ][crc]
[ idx0(off=0,  first=k000000) idx1(off=...,first=k000064)
  idx2(first=k000128) idx3(first=k000192) ][index crc]
[ footer ... ]
          ↑ 4 个索引项 = ceil(200/64)，即每 64 key 一个稀疏点
```

## 3. MANIFEST（段清单）

文件名固定 `MANIFEST`，纯文本、每行一条记录。每次 flush 或压实发布段集合时，
写 `MANIFEST.tmp` → fsync → `os.replace` 原子替换 → fsync 目录。读路径使用内存中
的段快照列表，不依赖该文件的实时读取。

```
lsmkv-manifest-v1        ← 魔数行
seq <u64>                ← 下一个待分配的 sequence
next-id <u32>            ← 下一个待分配的 segment id
level <n> <id> <id> ...  ← 第 n 层包含的段 id，按"从新到旧"顺序列出
...
end                      ← 结束行
```

- 段文件名与 id 一一对应：`seg-<id:08d>.sst`。
- 启动时：读 MANIFEST 确定存活段 → 删除任何不在清单中的 `seg-*.sst`/`*.tmp`
  （崩溃残留的孤儿段）→ 再重放存活 WAL。
- 压实发布是"用新清单整体替换旧清单"的原子操作：读线程持有的旧快照继续有效，
  旧段文件在 MANIFEST 落盘之后才删除。

---

## 4. 逻辑读取顺序（版本可见性）

一次 `get`/`scan` 的查找顺序（越靠前越新）：

1. 当前活跃 memtable（跳表）
2. 等待/正在刷盘的冻结 memtable（从新到旧）
3. 第 0 层段（从新到旧）→ 第 1 层 → ……更深层

第一个命中的版本即为最新版本：普通值返回该值；tombstone 视为"不存在"。
`get` 返回 `None` 表示 key 不存在，返回 `b""` 表示存在且值为空串，二者严格区分。
